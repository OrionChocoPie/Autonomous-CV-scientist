# Строгие правила работы кодинг-агента

Эти правила обязательны для любой задачи в этом проекте. Если правило нельзя выполнить — остановиться, назвать причину и что именно блокирует, а не обходить молча.

## 1. Перед началом работы

1. Сначала прочитать задачу целиком и переформулировать её как чек-лист требований, включая граничные случаи и негативные сценарии («ошибка если X», «no-op если Y»).
2. Сначала изучить репозиторий: структуру, существующий код по теме, соседние тесты, конфиги, `pyproject.toml`. Не писать код, не прочитав код, который меняешь, и его вызывающие места.
3. Для бага — сначала воспроизвести падение на реальном коде (тест или скрипт в `/tmp`). Нет воспроизведения — нет фикса.
4. Для задачи из 3+ шагов — составить todo-план и вести его по ходу работы.
5. Если требование допускает два материально разных прочтения (интерфейс, формат данных, поведение для пользователя) — задать один сгруппированный вопрос до написания кода. Локально проверяемые факты не спрашивать — проверять самому.

## 2. Объём изменений

1. Делать ровно то, что попросили. Никаких «заодно» рефакторингов, новых фич, панелей, флагов и абстракций вне задачи.
2. Чинить корневую причину, а не симптом. Один минимальный фикс вместо серии пробных правок.
3. Не вводить новые зависимости без явной необходимости; предпочтение — стандартная библиотека и уже установленные пакеты.
4. Совместимость: не менять публичные API, форматы данных и поведение существующих тестов без явного указания в задаче.
5. Не трогать файлы вне области задачи. Не удалять и не переиспользовать чужие untracked-файлы.

## 3. Код

1. Следовать стилю окружающего кода: имена, типы, обработка ошибок, структура модулей.
2. Никаких пустых `except: pass` и молча проглоченных ошибок. Ошибка либо обрабатывается осмысленно, либо пробрасывается.
3. Никаких секретов, токенов и абсолютных путей разработчика в коде.
4. Никакого закомментированного мёртвого кода и отладочного `print` в готовом изменении. Логи — только через принятый в проекте механизм.
5. Комментарии — короткие и по делу: что и почему, без рассуждений вслух.
6. Новая функциональность покрывается тестом в `tests/` в том же изменении, а не «потом».

## 4. Дебаг

1. Одна гипотеза за раз: сформулировать, проверить экспериментом, зафиксировать результат. Не менять несколько вещей одновременно.
2. Сначала доказательства, потом вывод: читать логи, стектрейсы и реальные данные, а не гадать по описанию.
3. Если собственный проверочный скрипт расходится с поведением кода — считать багом скрипт, а не ослаблять код под тест.
4. Не «чинить» тест под сломанный код. Падающий тест по изменённой области — это требование, а не шум. Никаких `skip`/`xfail`/ослабления ассертов ради зелёного прогона.
5. Если фикс не помог с двух попыток — остановиться, перечислить проверенные гипотезы и результаты, и только потом пробовать другой подход.

## 5. Проверка (обязательна перед «готово»)

1. Запустить тесты изменённой области через окружение проекта: `source .venv/bin/activate && python -m pytest tests/ -q`. Считать результат только из фактически завершённого прогона в этой сессии.
2. Заявка «работает» без запущенной проверки запрещена. Если проверить нельзя — прямо написать, что именно не проверено.
3. Проверить не только happy path: пустой ввод, `None`, отсутствующий файл, повторный запуск, граничные значения.
4. Перед финальным ответом перечитать исходную задачу и отметить каждый пункт чек-листа: сделано / не сделано / не проверено.
5. После установки пакетов или генерации файлов — проверить `git status` (если репозиторий инициализирован) и убрать побочные изменения, которые не нужны задаче.

## 6. Окружение и Git

1. Python-окружение — только `.venv` внутри проекта. Никаких установок в системный интерпретатор, никакого `--break-system-packages`. Команды запуска в ответе — против `.venv`.
2. Без явной просьбы пользователя в этой сессии: не коммитить, не пушить, не делать `amend`, `rebase`, `reset --hard`, не удалять ветки и теги.
3. Не убивать чужие процессы и не останавливать сервисы, которые не запускал сам. Для своей проверки — отдельный свободный порт.
4. Не трогать `.venv/`, кэши и сгенерированные артефакты как «исходники».

## 7. Коммуникация

1. Отвечать на языке пользователя, коротко и по делу, без похвалы и воды.
2. Финальный ответ: сначала результат, затем — что изменено (файлы), что запущено и что реально наблюдалось (вывод тестов), что не проверено и почему.
3. Никогда не выдумывать: вывод команд, цифры, URL, поведение библиотек. Не уверен — проверить или пометить как непроверенное.
4. Если нашёл постороннюю поломку вне задачи — сообщить как находку, а не чинить молча и не блокировать ею сдачу своей задачи.
5. Если инструкция пользователя противоречит этим правилам (например, «пропусти тесты») — выполнить инструкцию, но одной строкой отметить, какое правило при этом нарушено.

## 8. Критерий «готово»

Задача сдана только когда одновременно:

- [ ] каждое требование из чек-листа (п. 1.1) проверено по реальному коду;
- [ ] тесты изменённой области запущены в этой сессии и зелёны;
- [ ] нет побочных изменений вне области задачи;
- [ ] финальный ответ называет изменённые файлы, запущенные проверки и непроверенные места.
